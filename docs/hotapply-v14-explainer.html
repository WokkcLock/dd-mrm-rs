dd-mrm 热修改 v14：写盘 + size 守卫 + 仪式{#hotapply-v14}

长图

答

结论

现行方案（v14，B 路线）：游戏运行中点一次应用，工具用生产代码原子写入存档；DLL 守卫在查询出口抹平 size 缓存；用户重看一次开场动画，游戏自己把新文件完整读进内存。平时零后台、零轮询、零管道，只在点应用那一刻工作。

  1. 断言是唯一崩溃根因：旧 size 触发 GetStringData 检查，守卫在出口改写成磁盘真值，前提永不成立。
  2. 内容层永远来自磁盘：外部工具保真写盘即可，完全不必碰游戏内部对象。
  3. refresh 在进屏时九槽全量重读：仪式就是借用游戏自己的加载动作，不是外挂逻辑。
  4. 零写死地址：每次注入现场做指纹定位，失配即安全中止、不写盘不崩溃。

适用于dd-mrm-rs hotapply v14（2026-11-16 B 路线定案）· Darkest.exe x64偏移以该版实测为准

一次应用的全链路{#apply-flow}

图的结构
  • 用户 u
  • dd-mrm 工具 t
  • 守卫 DLL d
  • Darkest.exe g
  • persist.game.json k
  • steam.exe s
  • u → t · 点「应用」
  • t → g · 定位指纹 + 写 cfg v8 + 注入 DdHotapply.dll
  • g → d · LoadLibrary 校验指纹装钩
  • t → k · 原子写 persist.game.json
  • u → g · 重看开场动画
  • g → k · refresh 九槽重读（守卫校正 size）
  • g → s · 退出存档交 Remote Storage
  • s → k · 照常回写（实测确认游戏已吃进）
  1. 冷路径（游戏没开）

    直接写盘即可：下次启动必读新文件，无需注入与仪式。

  2. 热路径判定

    备份后重查进程防 TOCTOU；热修改关闭则走纯文件写盘并提示退出覆盖风险。

  3. 守卫失败即中止

    ensure_hooked 失败 = 报错且不写盘；宁可不做，不可做错。

  4. 仪式文案

    写盘成功后状态栏给出操作指引；用户照做一次即生效。

3

为什么必须守卫？{#why-guard}

游戏读 persist 走三层：size 查询、按大小分配缓冲、Reader 拷内容。size 有长寿命缓存（Steam Auto-Cloud 层之下），游戏自己读成功都不刷新；同一会话内外部改文件，缓存旧 size 小于新实际长度，断言弹窗，选调试即崩溃。

  1. 取 size

    fs_get_file_info（sub_140247F30）走缓存出旧值

  2. 分配

    游戏按旧 size 分配读缓冲

  3. 校验

    文件内联长度 array_size 对比 buffer_size，违者弹断言

  4. 守卫落点

    钩在查询出口，把 size 改成磁盘真值，链条断在这里

实测：守卫让断言前提消失

E1d：陈旧 3932 被校正为真值 3944，共 7 次全中，卡名即时更新，零断言。E1e：三轮摘加 mod（3944→3828→3732→3824），FIX 共 39 次完全对称，皮肤肉眼确认来回切换。E2：DLL v14 全流程用户实测通过（2026-11-16）。

哪些路走不通，为什么？{#history}

方案一行结论
v1/v2 帧一体化吃旧版红利：帧函数每帧被调 + 保存一体；2026-11-05 更新双前提齐灭
v3..v16 泵/两段式系列十七轮全败：脏标志挡写、载入覆盖内存态、断言频发
v17 重放（调包+自消费）链路全通但保存被脏标志挡住，载入又洗掉内存改动
v19 纯写盘（裸 A）证伪：同一会话陈旧 size 必触发断言（E1d）
v14 现行（B 路线）写盘 + 守卫 + 仪式；E1d/E1e/E2 三级实测通过

写盘者从来不是游戏进程

E1a/E1d 观测：游戏从不直接写存档盘，写盘者是 steam.exe（Remote Storage IPC）；退出存档时它按游戏内存态无条件回写。因此仪式后游戏吃进新内容，下次退出自动落盘，工具无需再做什么。
